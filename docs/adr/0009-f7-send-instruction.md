# ADR-0009 指示送信（F-7）の実現手段と安全性

- 日付: 2026-09-04
- 状態: **提案（人間の承認待ち）**。承認後に §「決定」を「採用」に改め、TASKS.md の T-030 以降を `todo` にする
- 関連: harness.md §1.2 F-7 / §2.4 / §9.2 / §9.3, RESEARCH.md §6, ADR-0003, ADR-0005

## 文脈

第 1 段階（read-only）は PR #33 で完了した。利用者から第 2 段階への着手が承認されたため、harness.md §2.4 のとおり「実現手段と安全性を ADR にまとめ、人間の承認を得てからタスク化する」。
本 ADR は 2026-09-04 に実機（Claude Code 2.1.241 / Codex CLI 0.152.1、Windows 11 ネイティブ）と公式ドキュメントで確認した事実に基づく。

## 確認できた事実

### Claude Code

1. **稼働中セッションごとに受信箱（名前付きパイプ）がある。** `\\.\pipe\LOCAL\cc-msg-<hash>` が稼働セッション数ぶん実在し、`sessions/<pid>.json` の `messagingSocketPath` がそれを指す（RESEARCH.md §6.1 と同じ）。
2. **スクリプトからの投函は公式に想定されている。** 公式ドキュメント「Message your other Claude Code sessions」の「The session's inbox socket」節は「when you want a script or hook to post into a session」と明記し、接続の 1 行目に `{"type":"auth","token":"<token>"}` を送る手順を示す。ネイティブ Windows ではこの認証行が **必須** で、無い接続は閉じられる。トークンは「自分の OS ユーザーだけが読める鍵」で、実機では `sessions/<pid>.<sha256>.key`（83〜111 バイト）がそれに相当すると推測される（内容は未読）。
3. **認証行の後に送るメッセージ行の形式はドキュメントに無い。** 取得した範囲（cross-session-messaging、env-vars、hooks、errors の各ページ）に JSON のフィールド名は記載されていない。実装前に確認が要る。
4. **受信側の安全弁は Claude Code 自身が持つ。** 受信側は「他セッションからのメッセージ」として扱い、承認の代行や設定変更はできず、コマンドは実行されず、権限プロンプトは通常どおり出る。`crossSessionInbound` が未設定なら、受信側が権限を省略するモード（bypass / auto を含む）のときは **保留して人間の承認ダイアログを出す**。送信元を検証できないメッセージも同じく保留される。1 セッションあたり 50 件のキュー、連投は送信側で拒否、同一内容の連投は破棄される。
5. **配信されたメッセージは利用者が打った prompt と同じく使用量に数えられる。** 受信側が idle なら新しいターンが始まる。
6. **`claude agents --json` が稼働中セッションの一覧（`pid` / `cwd` / `kind` / `startedAt` / `sessionId` / `name`）を返す。** 表示名 `name` は `sessions/<pid>.json` に無い情報で、F-6 の改善にも使える。
7. **`claude -p --resume <sessionId> "<prompt>"` は公式に「既存セッションへ追加の prompt を送る」用途で案内されている**が、「同じセッションを 2 つの端末で fork せずに再開すると、両方のメッセージが 1 つの transcript に混ざる」とも明記されている。稼働中セッションに対して使うと JSONL の並行書き込みになる。課金も発生する。
8. **channels（MCP サーバから push）は研究プレビューで、セッション起動時に `--channels` で許可リスト内のプラグインを指定した場合にだけ有効。** 既に起動している任意のセッションへ外から届ける手段にはならない。
9. **agent view（`claude --bg` / `claude attach`）** はバックグラウンドセッションの起動と対話用で、外部から prompt を投函するファイルやソケットのプロトコルは公開されていない。
10. `claude inject` のような公式 CLI は無い（GitHub issue #24947 は closed だが対応する CLI は 2.1.241 に存在しない）。

### Codex CLI

11. **`codex queue --thread <UUID|名前> --message <text>` が存在する**（「Queue a message for an existing session」）。`codex agents` は「shared local app-server daemon 上の全エージェントセッション」を一覧するため、queue はこの daemon 経由で届く可能性が高い。**対話 TUI として起動しただけのセッションに届くか、daemon が必要かは未確認**（実機に稼働中の Codex セッションが無く試せなかった）。
12. `codex exec resume <SESSION_ID> [PROMPT]` は非対話で既存セッションを再開する。Claude の `--resume` と同様に、稼働中セッションに対しては rollout の並行書き込みと課金のリスクがある。

## 選択肢

| # | 手段 | 対象 | 稼働中に届くか | 課金 | ログ破損 | 秘密情報 | 判定 |
|---|---|---|---|---|---|---|---|
| A | 名前付きパイプへ投函（公式の inbox socket 手順） | Claude | **届く**（idle なら新ターン、実行中ならツール呼び出しの合間に読む） | 受信側で prompt と同じ扱い | なし（Claude Code 自身が書く） | `.key` を読んで認証行に使う | **採用候補** |
| B | `claude -p --resume` を子プロセスで実行 | Claude | 稼働中は不可（transcript が混ざる）。停止中のみ | 発生 | 稼働中に使うと発生 | なし | 停止中セッション限定の補助案。第 2 段階では **採らない** |
| C | channels（MCP push） | Claude | `--channels` 付きで起動したセッションだけ | 受信側 | なし | プラグイン許可リストが必要 | 汎用性が無く **採らない** |
| D | 端末ウィンドウへのキー送出（SendKeys / UI Automation） | 両方 | 届くが脆い | 受信側 | なし | なし | 誤送信・取りこぼしが多く **採らない** |
| E | `codex queue --thread --message` | Codex | **要検証**（daemon 経由の可能性） | 受信側 | なし | なし | **採用候補** |
| F | `codex exec resume` | Codex | 稼働中は不可 | 発生 | 稼働中に使うと発生 | なし | 第 2 段階では **採らない** |

## 決定（提案）

1. **Claude Code への送信は A（名前付きパイプ）で実装する。** Codex への送信は E（`codex queue`）で実装する。B / F は「停止中セッションへの再開」として第 3 段階以降に別 ADR で扱う。
2. **実装前に検証スパイク（T-030）を行い、次を確かめてから本実装に進む。**
   - `.key` の内容が認証行の `token` そのものか（形式の確認。値はログ・PR・テストに一切書かない）
   - 認証行の後に送るメッセージ行の JSON 形式（利用者自身が起動した使い捨ての `claude -p` セッション、または本ダッシュボード開発中のセッションに向けて、`ListAgents` / `SendMessage` と同じ結果になる行を特定する）
   - 受信側が auto / bypass のとき保留ダイアログが出ること、prompting のとき配信されること
   - `codex queue` が対話 TUI セッションに届くか、daemon（`codex app-server daemon`）が要るか
   スパイクは **利用者が起動した検証用セッションだけ** を相手にし、稼働中の作業セッションには送らない。
3. **安全側の設計（harness §9.3）**
   - 既定は読み取り専用のまま。送信は `ReadOnlyToggle` を OFF にし、さらに送信前の確認ダイアログ（宛先セッション名 / cwd / 本文の先頭 200 文字）を経てからだけ実行する。ダイアログは色だけで区別せず「送る」ボタンを唯一の `primary` にする（DESIGN.md §6.6）。
   - 宛先は索引が持つ稼働中セッション（`running`）だけ。`sessionId` と `pid` と `messagingSocketPath` が `sessions/<pid>.json` の同一レコードから来たものに限り、パイプ名は `\\.\pipe\LOCAL\cc-msg-` 前置きの厳密一致で検証する。ユーザー入力からパイプ名やパスを組み立てない。
   - `.key` の読み取りは送信の瞬間だけ行い、メモリに保持しない。API 応答・ログ・エラーメッセージ・テストに値を出さない。読み取り対象は `sessions/<pid>.<64 hex>.key` の形式に一致するファイルだけで、`isExcludedFile` の `*.key` 除外は **この 1 経路だけ** 例外にする（ARCHITECTURE.md §7 に明記）。
   - 送信 API は `POST /api/sessions/:tool/:id/message`。本文は 1〜4,000 文字、1 セッションあたり 10 秒に 1 件、同一本文の連投は拒否（受信側の制限より厳しくする）。CORS は既存どおり `localhost` / `127.0.0.1` のみ。
   - 送信本文とその結果は **ログに出さない**（件数と成否のみ）。
   - 子プロセス（`codex queue`）は `execFile` で固定引数・シェル非経由・10 秒タイムアウト（`process/list.ts` と同じ規約）。
4. **停止条件（harness §9.2）との関係**
   - `.key` の読み取りは §9.2-2（秘密情報に触れる）に該当するため、本 ADR の承認をもって「この 1 経路だけ許可」とする。
   - 受信側での使用量発生は §9.2-3（課金）に該当するため、同じく承認の対象とする。検証スパイクで消費するのは利用者が起動した検証用セッション分のみ。
   - `~/.claude` / `~/.codex` への書き込みは行わない（パイプへの投函と `codex queue` は Claude Code / Codex 自身が処理する）。

## 結果

- 承認されれば T-030（検証スパイク）→ T-031（サーバ: 送信 API とパイプ / queue のアダプタ）→ T-032（クライアント: `ComposeBox` の有効化と確認ダイアログ）→ T-033（E2E とドキュメント）の順で進める（TASKS.md）。
- スパイクでメッセージ行の形式が特定できない場合、または `codex queue` が TUI セッションに届かない場合は、その側の送信を第 2 段階から外し、利用者に報告して方針を変える（同じやり方で 4 回目を回さない）。
- 承認されない場合は、`ComposeBox` は無効のまま第 1 段階の状態を維持する。

## 承認を求める点（利用者へ）

1. Claude への送信手段として **名前付きパイプ（A）** を採ること。`sessions/<pid>.<sha256>.key` をダッシュボードが **送信時にだけ読む** ことを許可するか
2. Codex への送信手段として **`codex queue`（E）** を採ること
3. 検証スパイク（T-030）で、利用者が起動した検証用セッションに数件のメッセージを送り、その分の使用量が発生することを許可するか
4. 送信の UI 方針: 読み取り専用トグル OFF + 送信前確認ダイアログの 2 段階でよいか
